# /obsidian-tasks Skill

## 何をする skill か
この skill は、`obsidian/tasks/` ディレクトリ内で task ファイルを作成、コメント追加、クローズするためのガイドラインと操作ルールを提供する。
主な目的は次の 3 つ。

1. 作業中に気づいたバグ・技術的負債・改善点を適切に記録する
2. 既存 task に関連する作業をしたときに、適切にログを追記する
3. task の状態管理（todo/wip/done）をルールに従って行う

## 使う場面
- バグや改善点を見つけたときに記録したい
- 既存 task に関連する作業をしたときに、その内容を記録したい
- task をクローズしたいときに、適切な手順で行いたい

## ディレクトリ構成
### obsidian/
ここ以下に task ファイルや他に必要なファイルを格納する。
ここ以下で作成更新したファイルについては commit しない。

task 以外のファイルが必要な場合は、`obsidian/` 以下にディレクトリを作成し、その中に格納すること。

### obsidian/tasks/
この直下にすべての task ファイルが格納される。

### obsidian/tasks/archived/
ここには、過去の task ファイルで、現在は参照する必要がないものを移動することができる。これらはクローズされた task とは異なり、完全にアーカイブされた状態で保持される。エージェントは参照・更新の対象としない。


## ファイル命名規則
{number}-{title}.md
number は 4 桁の連番で、0001 から始まる。新しい task を作成するときは、ファイルの中で最大の number に 1 を足したものを使用する。
title は kebab-case の英語で、理解のしやすい短い文章を用いる。
記号などは適切にサニタイズすること。
例: `0001-fix-authentication.md`

## ファイルフォーマット

```markdown
---
title: {タイトル}
status: {todo|wip|done|cancelled}
---

# 概要

# 背景

# 実装/修正プラン

# ログ

## {YYYY-MM-DD HH:MM} {エージェント名} {モデル名}
{本文}

```

ログは時系列で末尾に追記していく。
既存のログが時系列の逆順で書いてある場合でも、それを無視して末尾に追記すること。
どのような内容を含めても良いが、以下に示すものがある場合は必ず追記する。
日時については基本的に日本時間(UTC+9、夏時間なし)で記録する。それ以外のタイムゾーンで記録する場合は、必ずタイムゾーンを併記すること。

- どのような変更が行われたか
- なぜその変更が行われたか
- 重要な実装上の詳細
- 今回あえて対応しなかった内容

## 操作ルール

### 共通・全体ルール
- 1つの task につき1ファイル
- 添付ファイルや、関連する複雑な情報などを保持する必要がある際は、ファイル名と同名のディレクトリを作成し、その中に入れること
- 必要なタイミングでの更新は確認せずに行って良いが、task の状態に影響する場合は、必ずログに記録すること

### 起票
- 新しい task を起票するときは、`obsidian/tasks/` ディレクトリにファイルを作成し、status は `todo` にすること
- タイトルは1行で内容を適切に要約したものを `# ` の後に書くこと。ファイル名と異なっていて良い
- 概要、背景、実装/修正プランは必要に応じて記入するが、空欄でも構わない

### 実装
- task に対して実装や修正を行うときは、必ずログに記録すること
- 実装を行う際は、task の status を `wip` に変更する
- 実装前に、実装/修正プランを確認し、必要に応じて更新すること
- 変更内容や理由、重要な実装上の詳細などを記録することが望ましい
- 変更内容が大きい場合や、複数の変更がある場合は、複数回に分けてログに記録することも可能
- 実装の途中で新たな問題を発見した場合は、その内容もログに記録することが望ましい
- 実装の途中で新たな問題を発見し、現在の task の範囲外と思われる場合は別の task を起票する


### コメント・ログ
- 既存 task で追跡しているバグ・負債・改善点に直接対処する変更を行ったとき、または task の状態に影響する作業をしたときは、該当ファイルの `## ログ` に追記する
- 単なる参照や間接的な関連は追記しなくともよい
- ログを書き込む際、過去のログは編集せず、必ず追記で行うこと
- ログには、変更内容や理由、重要な実装上の詳細などを記録することが望ましい
- ログには感想や考察なども含めて構わないが、内容が task の状態や今後の作業に影響するものであれば、必ず記録すること

### クローズ
- task をクローズするときは、ファイルの `status` を `done` に変更する
- クローズするときは、ユーザーに確認を求め、OKをもらった際に、最後のログに「クローズ理由」を必ず記載する
